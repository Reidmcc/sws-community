# Contributing

Thanks for helping keep Squadrons alive. This page covers how changes get in, how to build and test, and the few rules
that protect players and the project.

## Ground rules

- **No game files or game data in the repo.** Players bring their own copy of the game. That means no exe, no assets,
  no extracted data, and no lists generated from the game's data, such as `unlock_ids.txt`. Where the mod needs to know
  something about the game's code, store hashes (see `mod/check_sites.h`) or offsets, never bytes.
- **Never connect to EA's servers with the mod loaded.** The mod is for self-hosted matches only, and the launcher
  refuses to run when EasyAntiCheat is running. Keep it that way.
- **Never modify the game's install folder.** The mod only reads from it.
- **No personal data in commits.** That includes logs, IP or Tailscale addresses, and user names. The `.gitignore`
  keeps logs and live configs out; check your diff anyway.
- **License:** contributions are under the project's license, [CC BY-NC-SA 4.0](LICENSE). It's non-commercial, by design.

## How changes get in

1. Branch from `main`, one branch per change, and open a pull request into `main`.
2. CI builds everything and runs the stand-in test on every pull request (`.github/workflows/build.yml`). It has to
   pass.
3. The maintainer ([Reidmcc](https://github.com/Reidmcc)) reviews and merges. For anything that changes gameplay, say
   in the pull request how you tested it in the game, or that you couldn't.

`main` is where tested changes land, and releases are the stable points. Players download releases (tags on `main`),
never `main` itself. A change that needs a wider test before it counts as stable goes out as a pre-release
(`v0.x.0-beta`).

Open an issue first for anything bigger than a fix, so we can agree on the approach before you build it.

## Building

You need Windows and Visual Studio 2022 with the C++ tools. The free "Build Tools for Visual Studio 2022" with the
"Desktop development with C++" workload is enough; Community or any other edition works too. The build scripts find
the compilers themselves (`mod/vsenv.bat`).

From `mod/`:

- `build_server.bat`: the server DLL (`sws_server.dll`), the launcher (`sws_launch.exe`), the store checker
  (`sws_check.exe`), the DLL's test build and the stand-in (`test_server_target.exe`).
- `build_app.bat`: the settings app (`sws_settings.exe`) and its self-test (`sws_settings_test.exe`).

Output goes to `mod/build/`, which git ignores. To play with your build, copy `mod/release/server.ini` and
`mod/release/profiles/` there; the README's Playing section covers the rest. `unlock_ids.txt` (everything unlocked)
comes from the game's data and isn't in the repo; the mod runs without it, minus the unlocks.

## Testing

**The stand-in test, without the game.** After building, with the game closed, from Git Bash:

```bash
bash mod/run_standin.sh
```

`test_server_target.exe` stands in for the game. It plants the game's real function prologues and data at the
addresses the DLL hooks, and the DLL's test build checks each hook's effect through the real launcher: the transport,
the value engine, limits, profiles and fingerprints, the material-grid settings, and more. It passes when it prints
`ALL PASS` and the settings app agrees with the DLL on the profile's fingerprint. Your own `server.ini`, `limits.ini`,
`defaults.ini` and `unlock_ids.txt` in `mod/build/` are saved first and put back afterwards.

**New behaviour gets a stand-in check, and the check gets a mutation.** Break the code on purpose (comment out the
fix, point an offset elsewhere), confirm the new check fails, then put the code back. A check that can't fail isn't
testing anything.

**In the game.** The stand-in can't tell you how the game behaves. For anything that changes gameplay, launch through
the settings app and play a match. The logs folder beside the DLL has a text log of what the mod did. For movement or
HUD values, tick **Record flight data for testing** on the app's Play page; `tools/observe_report.py` summarizes the
recording.

## Working on the DLL

- **`mod/sws_probe.cpp` is one source with several builds,** selected by defines: `SERVER` (the mod), `RULES`
  (movement rules), `PROBE_TEST` (hooks stand-in code instead of the game).
- **Hooks check the game's bytes before patching** (the site table's `expect` bytes). If the bytes differ (another
  build of the game), the mod refuses rather than patching blind. Every new site needs its real prologue planted in
  `test_server_target.cpp` too.
- **Never keep an engine pointer across a level change.** Grids, configs and components belong to the level that
  loaded them. Read what you need inside the game's own call, or re-find it.
- **The value engine's type table** (`mod/config_types.h`) is generated by `tools/gen_config_types.py` from the
  game's runtime type info, decoded from the exe. That decode isn't in the repo, because it comes from the game. If you
  need a type or field added, open an issue.
- **Limits** (`limits.ini`) come from `tools/gen_limits.py`, which reads the `defaults.ini` the DLL writes when the
  game runs. You can regenerate them after a launch.

`notes/` holds the research record. Before changing anything in an area, read the note for it: `test1-static-map.md`
(the running log), `socket-interface.md` (the transport), `exploits-code-map.md` (the movement rules) and
`material-grid.md` (damage against capital ships).
